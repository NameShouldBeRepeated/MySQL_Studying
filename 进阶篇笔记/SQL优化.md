# SQL优化

## 插入数据

- insert优化

  - 批量插入

    ```sql
    #一条一条插入
    INSERT INTO 表 VALUES(...);
    INSERT INTO 表 VALUES(...);
    INSERT INTO 表 VALUES(...);
    ...
    
    #批量插入
    INSERT INTO 表 VALUES(...),(...),(...);
    ```

  - 手动提交事务

    ```sql
    #一般的MySQL是自动提交事务的
    #我们可以手动提交
    START TRANSACTION;
    INSERT INTO 表 VALUES(...),(...),(...);
    INSERT INTO 表 VALUES(...),(...),(...);
    INSERT INTO 表 VALUES(...),(...),(...);
    INSERT INTO 表 VALUES(...),(...),(...);
    ...
    COMMIT;
    ```

  - 主键顺序插入

    ```sql
    #主键乱序插入：6 5 8 3 2 9 7 4 1；
    #主键顺序插入：1 2 3 4 5 6 7 8 9；
    顺序插入的性能明显好于乱序插入
    ```

- 大批量插入数据

  如果一次性需要插入大量数据，insert的插入性能就不够用了，此时可以使用MySQL数据库提供的load指令进行插入。具体操作如下：

  ```sql
  #客户端连接服务端时，加上一条参数 --local-infile
  mysql --local-infile -u root -p
  #设置全局参数local_infile为1，开启从本地加载文件导入数据的开关
  SET GLOBAL local_infile = 1;
  #执行load指令，将准备好的数据加载到表结构中
  LOAD DATA LOCAL INFILE '文件路径' INTO TABLE '表名' FIELDS TERMINATED BY '每个数据的分隔符（如果是逗号分隔的就写,）' LINES TERMINATED BY '每一行的分隔符（如果是回车换行的话就写\n）'
  ```

  这种方法插入时，也是**主键顺序插入性能高于乱序插入**

- 数据的组织方式

- 页分裂

  页可以为空也可以填充一般，还可以填充百分之百。每个页包含了2-N行数据（如果一行数据过大，会行溢出），根据主键排列

  ![Snipaste_2026-10-15_19-46-19](..\images\Snipaste_2026-10-15_19-46-19.png)
  
  上述这种情况叫做**页分裂**

- 页合并

  在删除一行记录时，实际上记录并没有被物理删除，只是记录被标记（flaged）为删除并且它的空间变得允许被其他记录声明使用

  当页中删除的记录达到 MERGE_THRESHOLD（默认为页的50%），InnoDB会开始寻找最靠近的页（前或后）看看是否可以将两个页合并以优化空间使用

  > 把后继的合并了，优化空间

- 主键设计原则
  - 满足业务需求的情况下，尽量降低主键的长度
  - 插入数据时，尽量选择顺序插入，选择使用AUTO_INCREMENT自增主键
  - 尽量不要使用UUID（随机字符串）或者其他自然主键，如身份证号
  - 业务操作，尽量避免对主键进行修改

## order by优化

Using filesort：通过表的索引或全表扫描，读取满足条件的数据行，然后再排序缓冲去sort buffer中完成排序操作，所有不是通过索引直接返回排序结果的排序都叫FileSort排序

Using index：通过有序索引顺序扫描直接返回有序数据，这种情况叫using index，不需要额外排序，操作效率高

在业务操作中，尽量让`Using index`使用的更多

- 根据排序字段建立合适的索引，多字段排序时，也遵循最左前缀法则
- 尽量使用覆盖索引
- 多字段排序，如果一个升序一个降序，此时注意联合索引在创建时的规则(ASC/DESC)
- 如果不可避免的出现FileSort，大数据量排序是，可以适当增大排序缓冲区大小sort_buffer_size（默认256k）

## limit 优化

 ```sql
SELECT ... LIMIT 0,10;#运行很快，意思是从0开始往后找十条
SELECT ... LIMIT 2000000,10;#运行很慢，此时要排序前2000010条记录，只返回2000000-2000010的记录，其他记录丢弃，这样代价太大了
 ```

优化思路：一般分页查询时，通过创建**覆盖索引**能比较好的提高性能，可以使用覆盖索引+子查询形式的优化

```sql
EXPLAIN SELECT * FROM tb_sku t ,(SELECT id FROM tb_sku ORDER BY id LIMIT 2000000,10) a WHERE t.id = a.id
```

## count优化

不同存储引擎的count方式不一样

- MyISAM引擎把一个表的总行数存在磁盘上，因此执行count(*)的时候会直接返回这个数，效率极高
- InnoDB引擎执行count(*)，要把数据一行一行从引擎里面读出来再计数，效率很低

优化思路：自己计数

- count的几种用法

  - count()是一个聚合函数，对于返回的结果集，一行一行地判断，如果count函数的参数不是NULL，累计值就加1，否则不加，最后返回累计值

  - 用法：count(*)、count(主键)、count(字段)、count(1)

    - count（主键）

      InnoDB引擎会遍历整张表，把每一行的主键id值取出来，返回给服务层，服务层拿到主键之后，直接按行累加（主键不可能为NULL）

    - count（字段）

      没有not null 约束：InnoDB引擎会遍历整张表把每一行的字段值都取出来，返回给服务层，服务层判断是否为null，不为null，计数累加

      有not null约束：InnoDB引擎会遍历整张表把每一行的字段值都取出来，返回给服务层，直接按行进行累加

    - count（1）

      InnoDB引擎遍历整张表，但是不取值，服务层对于返回的每一行，放一个数字“1”进去，直接按行进行累加

    - count（*）

      InnoDB索引不会吧全部字段取出来，而是专门做了优化，不取值，服务层直接按行进行累加

  * 效率排序

    **count（字段）<count（主键）<count（1）≈count（*）**，所以说尽量使用count（*）

## update优化

```sql
UPDATE 表名 SET ... WHERE ;
```

上述操作时，where后面的条件如果是“索引”的话，那么只有这一行会被锁住，其余行依旧可以通过事务进行操作。但是如果where后面是一个普通字段或者索引失效，那么行锁会升级成表锁，整张表难以进行操作。极大影响并发效率
