# 索引

## 索引概述

**介绍**

索引（index）是帮助MySQL高效获取数据的数据结构（有序）。数据之外，数据库系统还维护中满足特定查找算法的数据结构，这些数据结构以某种方式引用（指向）数据，这样就可以在这些数据结构上实现啊高级查找算法，这种数据结构就是索引

**优缺点**

| 优势                                                         | 劣势                                                         |
| :----------------------------------------------------------- | :----------------------------------------------------------- |
| 提高数据检索的效率，降低数据库的IO成本                       | 索引列也是要占用空间的。                                     |
| 通过索引列对数据进行排序，降低数据排序的成本，降低CPU的消耗。 | 索引大大提高了查询效率，同时却降低了更新表的速度，如对表进行INSERT、UPDATE、DELETE时，效率降低。 |

## 索引结构

MySQL的索引在存储引擎层实现，所以不同的存储引擎有不同的结构

![Snipaste_2026-10-13_11-57-41](..\images\Snipaste_2026-10-13_11-57-41.png)

![Snipaste_2026-10-13_11-59-17](..\images\Snipaste_2026-10-13_11-59-17.png)

*平常提到的索引，如果没有特别指明，说的就是B+树索引*

**二叉搜索树**

极端条件下，会退化成一串链表，极大影响效率

**红黑树**

解决了二叉搜索树的问题，但是数据量极大的情况下，层级很深，检索速度慢

**B树（多路平衡查找树）**

以一颗最大度数为5（5阶）的B树为例（每个节点最多存**4个key，5个指针**）

![Snipaste_2026-10-13_12-10-07](..\images\Snipaste_2026-10-13_12-10-07.png)

**B+树**

以一颗最大度数为4（4阶）的B+树为例

![Snipaste_2026-10-13_13-37-16](..\images\Snipaste_2026-10-13_13-37-16.png)

> B+树只有叶子结点存数据！其余节点的数据都会在叶子结点中有一个一样的！

与B树的区别：

- 所有的数据都会出现在叶子结点
- 叶子结点会形成一个单向链表

**MySQL的改进版B+树**

原有B+树的基础上，增加了一个指向相邻叶子结点的链表指针，形成了有顺序指针的B+树，提高区间的访问性能

![Snipaste_2026-10-13_13-45-28](..\images\Snipaste_2026-10-13_13-45-28.png)

>双向链表的既视感，有效提高性能

**Hash**

哈希索引是采用一定的hash算法，将简直换成新的hash值，映射到对应的槽位上，然后存储在hash表中

*哈希冲突*

如果两个（或多个）键值，映射到一个相同的槽位上，他们就产生了hash冲突（也叫hash碰撞），可以通过链表来解决

>此处联想到JavaHashMap的底层，也是加链表解决。如果长度超过8，转换成红黑树（Java8以后）

![Snipaste_2026-10-13_13-50-36](..\images\Snipaste_2026-10-13_13-50-36.png)

Hash索引的特点

- 只能用于对等比较（= ，in），不能范围查询（between，<，>，...）
- 无法利用索引完成排序操作
- 查询效率高，通常只需要一次检索就可以，效率通常高于B+树索引

在MySQL中，支持hash索引的是Memory引擎，而InnoDB中有自适应hash功能，hash索引坏死存储索引根据B+树索引在指定条件下自动构建的

**思考题🤔**

Q：为什么InnoDB存储引擎选择使用B+树索引结构？

A：

- 相较于二叉树，层级更少，搜索效率高；
- B树的叶子结点和非叶子结点都会保存数据，这样导致一页中存储的键值减少，指针减少，要同样保存大量数据，只能增加书的高度，导致性能降低

- 相较于Hash索引，B+树支持范围匹配和排序操作

## 索引分类

![Snipaste_2026-10-13_14-07-26](..\images\Snipaste_2026-10-13_14-07-26.png)

在InnoDB存储索引中，根据索引的存储形式，又可用于分成以下两种：

![Snipaste_2026-10-13_14-09-43](..\images\Snipaste_2026-10-13_14-09-43.png)

聚集索引是一定存在的：

- 如果存在主键，主键索引是聚集索引
- 不存在主键，第一个唯一索引作为聚集索引
- 不存在主键，没有合适的唯一索引，那么InnoDB会自动生成一个rowid作为隐藏的聚类索引

![Snipaste_2026-10-13_14-24-15](..\images\Snipaste_2026-10-13_14-24-15.png)

> 右上是聚类索引，右下是二级索引。
>
> 聚类索引叶子结点存储的是整行数据，二级索引叶子结点存的是主键

由 InnoDB 的聚簇索引 / 二级索引分类，衍生出了**回表**这个内部执行步骤。它不是用户手动指定的查询方式，但是用户做索引设计和 SQL 优化时必须考虑。（注意！这是InnoDB自己的一种机制）

![Snipaste_2026-10-13_14-30-00](..\images\Snipaste_2026-10-13_14-30-00.png)

回表查询中，执行

```sql
SELECT * FROM user WHERE name = 'Ame'
```

会先去二级索引中查找'Ame'，找到主键，再去聚类索引里根据主键查到整行数据

**思考题🤔**

Q：以下SQL语句，那个执行效率高？为什么？

```sql
SELECT * FROM user WHERE id = 10;

SELECT * FROM user WHERE name = 'Arm'
```

> 注：id为主键，name字段创建的有索引

A：**第一条 `select \* from user where id = 10;` 执行效率更高。**

原因：

1. **`id` 是主键**。在 InnoDB 中，主键索引就是聚簇索引，叶子节点直接存储整行数据。所以 `where id = 10` 可以直接通过聚簇索引的 B+ 树定位到这一行，一次查找就能拿到 `select *` 需要的所有列，**不需要回表**。
2. **`name` 字段上创建的是二级索引**。二级索引的叶子节点只存储索引列（`name`）和主键值（`id`），并不包含整行数据。当执行 `select * from user where name = 'Arm'` 时：
   - 先在 `name` 二级索引中找到 `'Arm'`，拿到对应的主键 `id`；
   - 再拿这个 `id` 回到聚簇索引中查找完整行；
   - 这个过程就是**回表**，需要额外的 B+ 树查找和随机 I/O。

因此，虽然 `name` 上有索引，但 `select *` 需要所有列，导致必须回表，执行效率低于直接通过主键查询。所以第一条 SQL 效率更高。

## 索引语法

### 创建索引

```sql
CREATE [UNIQUE|FULLTEXT] INDEX index_name ON table_name (index_col_name);
#UNIQUE 唯一索引 FULLTEXT 全文索引 不写 默认普通索引
#(index_col_name) 指定索引列，可以是一列或者多列
```

### 查看索引

```sql
SHOW INDEX FROM table_name;
```

### 删除索引

```sql
DROP INDEX index_name ON table_name;
```

## SQL性能分析

**SQL执行频率**

MySQL客户端连接成功后，通过`show [session|global] status`命令可以提供服务器状态信息。通过如下指令可以查看当前数据库的INSERT、UPDATE、DELETE、SELECT的访问频次

```SQL
SHOW GLOBAL STATUS LIKE 'COM_______'
#一个下划线一个字母，查询出来的都是像“com_select”这样的，所以要有7个_
```

**慢查询日志**

慢查询日志记录了所有执行时间超过指定参数（long_query_time,单位：秒，默认10秒）的所有SQL语句的日志

MySQL的慢查询日志默认是不开启的，要在MySQL的配置文件（/etc/my.cnf）中配置如下信息：

```sql
#查看慢查询日志是否开启
show variables like 'slow_query_log';
#开启MySQL慢日志查询开关
show_query_log = 1;
#设置满日志的时间为2秒，SQL语句执行时间超过2秒，就会视为慢查询，记录慢查询日志
long_query_time = 2;
```

配置完成后重启MySQL。慢查询 日志文件在/var/lib/mysql/localhost-slow.log

**profile**

show profiles 能够在做SQL优化时帮助我们了解时间都耗费到哪里去了。通过have_profiling参数，能够看到当前MySQL是否支持profile操作

```sql
SELECT @@have_profiling;
#这个是查询数据库是否支持profile
```

默认profile是关闭的，通过set可以在session或者global中开启profiling

```sql
SET [SESSION|GLOBAL] profiling = 1;
#不加[SESSION|GLOBAL]默认范围是SESSION
```

开启后，可以通过指令查看SQL语句的执行耗时

```sql
#查看每一条SQL语句的耗时基本情况
show profiles;

#查看指定query_id的SQL语句各个阶段的耗时情况
show profile for query query_id;

#查看指定query_id的SQL与语句CPU的使用情况
show profile cpu for query query_id;
```

**explain执行计划**

EXPLAIN或者DESC命令获取MySQL如何执行SELECT语句的信息，包括在SELECT语句执行过程表如何连接和连接的顺序

```sql
#直接在select语句之前加上关键字explain/desc
EXPLAIN/DESC SELECT 字段列表 FROM 表名 WHERE 条件;
```

执行计划中个关键字的意思

- id

  select查询的序列号，表示查询中执行select自居或者是操作表的顺序【id相同，从上到下执行；id不同，值越大的越先执行（这种情况多见于子查询）】（多表查询中常用）

- select_type

  表示SELECT的类型，常见取值有SIMPLE（简单表，不使用表连接或者子查询）、PRIMARY（主查询，即外层的查询）、UNION（UNION（联合查询）中的第二个或者后面的查询语句）、SUBQUERY(SELECT/WHERE之后包含了子查询)等

- type

  表示连接类型，性能由好到差的连接类型为NULL，system，const，eq_ref，ref，range，index，all。

- possible_key

  显示可能应用在这张表上的索引，一个或多个

- Key

  实际使用的索引，如果为NULL，则没有索引

- Key_len

  表示索引中使用的字节数，该值为索引字段最大可能长度，并非实际使用长度，在不损失精确性的前提之下长度越短越好

- rows

  MySQL认为必须要执行查询的函数，在InnoDB引擎的表里，是一个估计值，可能并不总是准确的

- filtered

  表示返回结果的函数占需读取行数的百分比，filtered的值越大越好

## 索引使用

**验证索引效率**

经过验证，加索引之后再查询，快的不是一点半点

**最左前缀法则**

如果索引了多列（联合索引），要遵循最左索引法则。最左索引法则指查询时从索引的最左列开始，且不能跳过索引中的列，也就是不能间隔使用

如果跳跃某一列，**索引将部分失效（后面的字段索引失效）**

比如：联合索引组合（A，B, C），那么能生效的索引（A）（A, B） (A , B, C)[顺序没有要求！（B，A，C）也能生效]，如果使用（A，C）做条件，会部分失效，C失效（即查询很慢，不走索引）。

> deepseek的评价
>
> 联合索引 `(A,B,C)` 遵循最左前缀原则。查询条件想利用该索引进行定位，通常需要包含最左列 `A`，并在 `A` 等值的前提下连续包含 `B`，才可能继续用 `C`。如果写成 `WHERE A=? AND C=?`，通常只能用 `A` 做索引查找，`C` 不能用于缩小索引范围，但可能通过索引条件下推参与过滤；是否走索引、快慢取决于优化器成本和数据分布，不能断言“不走索引”或“一定很慢”。`

**范围查询**

联合索引中，出现范围查询（>，<），**范围查询右侧的索引失效**

但是！！！（>=，<=），会比（>，<）快一点，所以实际工作中在不改变业务语义的前提下尽量使用>=，<=

**索引列运算**

！不要在索引列上进行运算操作！，**索引将失效！**

**字符串要加引号**

虽然有时候不加引号也能查出来（比如电话号码），但是**不加引号索引失效！**

**模糊查询**

如果仅仅是尾部模糊匹配，索引不会失效。**如果是头部模糊匹配，索引失效**

也就是’abc%‘可以走索引，但是’%abc‘走不了索引
